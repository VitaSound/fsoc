# Design

## Context

См. proposal.md — Why. Шина `io` J1: адрес — `mem_addr[15:0]`, устройство выбирается одним битом адреса (не диапазоном), стробы `io_rd` / `io_wr`, данные `dout` / `io_din`. Заняты биты 10–13; в словаре SwapForth упоминаются `4 io!` (`leds`) и биты 14–15 (`tasksel`), в обёртке их нет. `csr.4th` сейчас — линейная карта с шагом 4 байта в стиле LiteX CSR, не совпадающая с реальной битовой шиной.

## Goals / Non-Goals

**Goals:**

- Адрес устройства написан один раз, в Forth.
- Прошивка, обёртка и хост читают один и тот же экспорт.
- Тест доказывает согласованность, а не только существование файлов.

**Non-Goals:**

- Генерация `j1_wrap.v` из fhdlgen (следующий шаг, roadmap path 1); здесь обёртка остаётся `.v` и читает `iomap.vh`.
- Линейная CSR-шина LiteX-стиля, Wishbone, контроллер прерываний.
- Новые устройства на шине: карта описывает четыре существующих.

## Decisions

1. **Модель — бит-селект, не база+смещение.** `io-dev ( name bit width flags -- )`; адрес устройства = `1 << bit`. Это честно отражает `j1_wrap.v` и позволяет `io_din` собираться `|` по битам. Альтернатива — сохранить линейную карту `csr.4th` и добавить декодер адресов в обёртку — дороже в LUT и меняет прошивку SwapForth (`io@`/`io!` по константам остаются, но `leds` и прочее сломается).

2. **Экспорт `csr.fs` — Forth-текст для SwapForth.** Формат: `$400 constant IO-LED` и так далее, `hex`-безопасно. Имя `csr.fs` (не `.4th`): файл подаётся в образ J1, а не в Gforth; расширение `.fs` уже используется прошивкой. `lamp.fs` начинается с `include csr.fs`; `soc-flatten` (из `emu-lib`) раскрывает его.

3. **Экспорт `iomap.vh` — `localparam`.** `localparam IO_LED_BIT = 10;` и т.д.; `j1_wrap.v` делает `` `include "iomap.vh" `` и пишет `mem_addr[IO_LED_BIT]`. Файл копируется в проект вместе с листами; `includes.lst` fhdlgen его не знает (это не `hdl-include-v`), поэтому копирует задача явно — это единственный не-лист файл, и он порождён самой задачей.

4. **Экспорт `csr.json` — `fjson.emit-*`.** Схема: `{"bus":"j1-io","devices":[{"name":"led","bit":10,"addr":1024,"width":1,"access":"rw"}, …]}`. Хосту (`fterm`, будущий CSR bridge) нужен `addr`, не `bit`; оба пишутся.

5. **Проверка согласованности — Icarus-стенд обёртки.** `rtl/tb_j1_wrap_io.v` подаёт запись по адресам из `iomap.vh` и читает обратно; Forth-тест сравнивает числа из `csr.fs`, `csr.json` и `iomap.vh` между собой (парсинг трёх текстов) и запускает стенд. Альтернатива — доверять одному генератору — не ловит ручную правку `.v`.

6. **`cores.4th` удаляется целиком.** Его имена (`ctrl`, `gpio`, `bus_errors`, `scratch`) не имеют железа; когда появится устройство — оно добавится в `iomap` строкой `io-dev`.

## Risks / Trade-offs

- [SwapForth `leds` использует `4 io!` — бит 2, в карте его нет] → карта описывает то, что есть в обёртке; `leds` в образе остаётся словом без устройства, как и сейчас.
- [`include csr.fs` в прошивке требует `soc-flatten` из `emu-lib`] → порядок изменений: `emu-lib` → `iomap`.
- [Изменение имён констант ломает пользовательские прошивки] → пользовательских прошивок кроме `lamp.fs` нет; имена фиксируются в спеке.

## Migration Plan

1. `iomap.4th` + три экспорта + тест согласованности на текущих адресах.
2. `j1_wrap.v` на `iomap.vh`; `lamp.fs` на `csr.fs`.
3. Удалить `cores.4th`, старый `csr_test`; документация.

Откат — вернуть литералы в `j1_wrap.v` и `lamp.fs`; экспорты безвредны.
